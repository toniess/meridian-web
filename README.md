# Сайт Игоря Глушкова — библиотека и «Меридиан»

Фронтенд на Next.js 15 (App Router, React 19, TypeScript) для Meridian API 1.0.0.
Две секции: **Библиотека** (книги, читалка, аудиокниги) и **Меридиан**
(лента записей проекта с фото, видео, документами и ссылками).

Оформление — направление «Лёд»: палитра снята с зимнего кадра на набережной
Иртыша. Заголовки Golos Text, текст книг Literata.

---

## Быстрый старт

```bash
npm install
cp .env.example .env
npm run dev              # http://localhost:3000
```

Если `API_BASE` не задан, сайт поднимается на встроенных демо-данных и
пишет об этом полоской сверху. Так можно работать над версткой, пока
бекенд занят.

Прод-сборка:

```bash
npm run build
node .next/standalone/server.js
```

## Как фронт ложится на API

| Эндпоинт | Где используется |
|---|---|
| `GET /api/library/books/` | `/` и `/library` |
| `GET /api/library/books/{slug}/` | `/books/[slug]` |
| `GET /api/projects/` | переключатель проектов, `/projects` |
| `GET /api/projects/{slug}/` | `/meridian`, `/projects/[slug]` |
| `GET /api/projects/{project_slug}/posts/` | лента проекта |
| `GET /api/projects/posts/{id}/` | `/posts/[id]` |

Весь обмен — в `lib/api.ts`. Пагинация DRF (`count / next / previous /
results`) разворачивается автоматически, до 20 страниц. Если бекенд
недоступен, страница показывает пустое состояние, а не падает с 500.

### Три места, где схема разошлась с интерфейсом

Это стоит прочитать, потому что здесь фронт делает допущения за бекенд.

**1. У книги нет глав — есть один файл.** В схеме `Book.file` это единая
ссылка, а текста в JSON нет вообще. Поэтому файл скачивается на сервере,
разбирается и режется на части:

- `txt`, `md`, `fb2`, `html` — читаются в читалке;
- `mp3`, `m4a`, `m4b`, `ogg`, `wav` и прочее аудио — книга становится
  аудиокнигой и открывается в плеере;
- `pdf`, `epub`, `docx` — читалка недоступна, страница предлагает скачать
  и честно объясняет почему.

Деление на части (`lib/content.ts`): если в тексте нашлось два и больше
заголовков — режем по ним, и названия рассказов попадают в оглавление.
Если заголовков нет — режем по объёму, примерно по 16 000 знаков, части
называются «Часть 1», «Часть 2».

Заголовком в обычном `txt` считается короткая одиночная строка без
завершающей точки. Это угадывает и «Глава третья», и просто
«Бортмеханик». **Если тексты будут грузиться в FB2, угадывать не
придётся вовсе** — там заголовки размечены явно, и это самый надёжный
вариант для сайта.

**2. Озвучек как отдельной сущности в API нет.** Сейчас аудиокнига — это
книга, у которой в `file` лежит аудио. Работает, но у такой книги нет
текста, и наоборот. Если нужно «читать и слушать одну и ту же книгу»,
бекенду понадобится второе поле (`audio_file`) или вложения у книги, как
у постов. На фронте это полчаса работы: плеер и разбор файлов уже есть.

**3. У записи нет ссылки на проект, а у постов нет slug.** Поэтому
адрес записи — `/posts/{id}`, а проект для хлебной крошки и навигации
«предыдущая-следующая» ищется перебором проектов. Проектов мало, ответы
кешируются, так что это дёшево. Если в `Post` появится `project` и
`slug` — адреса станут человекочитаемыми, а перебор уйдёт.

### Что ещё стоит добавить в API

- `excerpt` у поста — сейчас аннотация в ленте обрезается из `body`;
- порядок и сортировка книг — сейчас сортируем по `published_at` на фронте;
- `duration` у аудио — плеер умеет показывать длительность, но узнаёт её
  только после загрузки метаданных файла.

## Что уже работает

**Библиотека**: сетка книг, типографская обложка для книг без картинки
(цвет стабильно выводится из slug, так что книга без обложки выглядит
решением, а не пропуском), страница книги с оглавлением по частям.

**Читалка** `/read/[slug]/[часть]`: размер шрифта, ширина колонки, фон
(лёд / бумага / сепия) — настройки запоминаются в браузере; полоса
прогресса, оглавление в шторке, переходы между частями; последняя
открытая часть запоминается, и кнопка на странице книги превращается в
«Продолжить».

**Плеер** живёт в layout и переживает переходы между страницами: можно
слушать аудиокнигу и параллельно читать ленту. Перемотка, −15 секунд,
скорость 1–2×.

**Меридиан**: лента записей проекта, переключатель, если проектов
несколько, разбор `body` как лёгкого markdown (заголовки, цитаты,
ссылки) и все пять типов вложений из схемы — фото с подписью, видеофайл,
видео по ссылке (YouTube, VK, Rutube, Дзен — с автоопределением и
встроенным плеером), документ на скачивание, внешняя ссылка.

**Прочее**: адаптив до мобильных, клавиатурная навигация и видимый
фокус, `prefers-reduced-motion`, метаданные и OpenGraph, `sitemap.xml`
по реальным данным, `robots.txt`.

## Развёртывание в Cloud.ru Container Apps

Бекенд уже живёт там же, так что фронт разумно положить рядом.

### 1. Подготовка

Понадобятся Docker локально, аккаунт Cloud.ru и **персональные ключи
доступа** (Key ID и Key Secret) из личного кабинета.

### 2. Реестр в Artifact Registry

В личном кабинете: **Artifact Registry → Создать реестр**. Имя реестра
станет частью адреса: `<registry_name>.cr.cloud.ru`. Тип доступа —
приватный.

### 3. Аутентификация

```bash
docker login <registry_name>.cr.cloud.ru -u <key_id> -p <key_secret>
```

### 4. Сборка образа

Важно: **обязательно `--platform linux/amd64`**, иначе с Mac на Apple
Silicon соберётся arm-образ, который в Container Apps не запустится.

```bash
docker build --platform linux/amd64 \
  -t <registry_name>.cr.cloud.ru/glushkov-web:1.0.0 .

docker push <registry_name>.cr.cloud.ru/glushkov-web:1.0.0
```

Образ multi-stage на `output: 'standalone'`, весит около 150 МБ.

### 5. Создание контейнера

Создавайте контейнер **в интерфейсе Container Apps**, а не через быстрое
меню в Artifact Registry: быстрая форма не даёт задать переменные
окружения, а без `API_BASE` сайт поднимется в демо-режиме.

**Контейнеры → Container Apps → Создать**, дальше:

- **Образ** — `<registry_name>.cr.cloud.ru/glushkov-web:1.0.0`
- **Название контейнера** — глобально уникальное, из него получится адрес
  вида `<название>.containerapps.ru`. Например `glushkov`
- **Порт контейнера** — `3000` (именно на нём слушает Next.js)
- **Переменные окружения**:

  ```
  API_BASE=https://container-meridian.containerapps.ru/api
  NEXT_PUBLIC_SITE_URL=https://glushkov.containerapps.ru
  MERIDIAN_PROJECT_SLUG=meridian
  REVALIDATE_SECONDS=60
  NODE_ENV=production
  ```

  `NEXT_PUBLIC_SITE_URL` должен совпадать с реальным адресом сайта —
  иначе в `sitemap.xml` и OpenGraph уедут ссылки.

- **vCPU / RAM** — `0.5 vCPU / 1 GB` как рабочий минимум. На `0.1 vCPU /
  256 MB` Node поднимется, но первые отрисовки будут заметно медленные
- **Минимальное количество экземпляров** — `1`. Ноль означает, что
  контейнер засыпает и первый посетитель ждёт холодный старт
  (для сайта, который читают, это плохо; для экономии на первых порах —
  допустимо)
- **Максимальное количество экземпляров** — `2`
- **Публичный адрес** — включить

Создайте и дождитесь статуса «Выполняется». Адрес появится на странице
контейнера.

### 6. Проверка

```bash
curl -I https://<название>.containerapps.ru/
curl -s https://<название>.containerapps.ru/library | head -c 300
```

Если на страницах видна полоска «Демо-режим» — значит `API_BASE` не
долетел до контейнера: проверьте переменные окружения в ревизии.

### Автодеплой из GitHub

Репозиторий: https://github.com/toniess/meridian-web

Каждый push в `main` запускает два workflow:

- **check** — `npm run typecheck` и `npm run build`;
- **build & push** — собирает образ под `linux/amd64` и кладёт его в
  Artifact Registry под двумя тегами: `latest` и `sha-<коммит>`.
  Container App следит за `latest` и сам создаёт новую ревизию;
  `sha-…` остаётся в реестре, чтобы было на что откатиться.

Один раз нужно задать настройки репозитория:

```bash
gh variable set CLOUDRU_REGISTRY      --body '<registry_name>.cr.cloud.ru'
gh variable set IMAGE_NAME            --body 'glushkov-web'
gh variable set NEXT_PUBLIC_SITE_URL  --body 'https://glushkov.containerapps.ru'
gh secret   set CLOUDRU_KEY_ID        --body '<key_id>'
gh secret   set CLOUDRU_KEY_SECRET    --body '<key_secret>'
```

То же самое можно сделать руками: **Settings → Secrets and variables →
Actions**, вкладки Variables и Secrets.

Почему `NEXT_PUBLIC_SITE_URL` и `API_BASE` задаются здесь, а не только
в Container App: страницы пререндерятся во время `npm run build`. Адрес
сайта Next вообще подставляет литералом на этапе сборки, а без `API_BASE`
в образ попадут демо-данные с баннером «Демо-режим» — их будет видно,
пока не пройдёт первая ревалидация.

`API_BASE` и `MERIDIAN_PROJECT_SLUG` при этом нужны **и там, и там**: на
сборке — для пререндера, в Container App — для ревалидации и страниц,
которые рендерятся на каждый запрос.

В самом Container App нужно один раз выбрать образ с тегом `latest` и
включить автоматическое обновление ревизии при появлении нового образа.

### 7. Обновления

Каждая новая версия — новый тег и новая ревизия:

```bash
docker build --platform linux/amd64 -t <registry_name>.cr.cloud.ru/glushkov-web:1.0.1 .
docker push <registry_name>.cr.cloud.ru/glushkov-web:1.0.1
```

Затем в Container Apps создайте ревизию с новым тегом. Не используйте
тег `latest`: по нему невозможно откатиться, когда что-то сломается.

Автосборку из GitHub, GitLab или GitVerse можно настроить позже — Cloud.ru
поддерживает создание ревизии по пушу образа в реестр.

### Свой домен

Container Apps выдаёт адрес в `*.containerapps.ru`. Для собственного
домена привяжите его в настройках контейнера и не забудьте поменять
`NEXT_PUBLIC_SITE_URL` в переменных окружения.

### Про CORS

Его не нужно настраивать: к API ходит сервер Next.js, а не браузер
читателя. А вот **обложки, файлы книг и вложения постов браузер грузит
напрямую** — они должны отдаваться по HTTPS и быть доступны без
авторизации.

## Что заменить перед публикацией

- **Демо-данные** в `lib/mock.ts` — мои тексты, не авторские. После
  подключения `API_BASE` они не используются, но лежат в репозитории.
- **Контакты** в подвале (`components/Footer.tsx`) — ВК, телеграм, почта.
- **Биография** на `/about` захардкожена: в API нет сущности «автор».
- **Фотографии** в `public/images/` пережаты из присланных; если есть
  оригиналы побольше — положите их.

## Заметки на будущее

- **Шрифты** грузятся с Google Fonts через `<link>`. Для российской
  аудитории надёжнее положить `.woff2` в `public/fonts` и перейти на
  `next/font/local`.
- **Картинки** отдаются тегом `<img>`. Когда станет ясно, с какого хоста
  приходят обложки, имеет смысл перейти на `next/image` — хост бекенда
  уже прописан в `next.config.mjs`.
- **Поиск по библиотеке** и **RSS для ленты** ложатся на текущую
  структуру без переделок.
